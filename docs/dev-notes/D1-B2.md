## Migration plan
- Exactly 12 tables in `public`, with every column from doc 02.
- Additions:
  - `campaigns.stage` and `campaigns.buyer_test_email`, which `CampaignView` and later conversation creation need.
  - Usage counters live in `campaigns.budget_json.usage`.
- Composite tenant foreign keys everywhere, with `ON DELETE RESTRICT`. `messages (org, conversation_id, connection_id)` must match the conversation's own connection.
- Append-only rules:
  - `decisions` rejects every update except a single `blocked → resolved` change that sets a previously null `resolution_json`, and rejects deletes.
  - `evidence` is immutable.
  - The one exception is a tenant purge, scoped by the transaction-local `app.purge_tenant`, used only by the admin purge path.
- `app_private.is_member()` is `SECURITY DEFINER`, uses `search_path=''`, and lives in a schema the Data API doesn't expose. This avoids RLS recursion.
- Row-level security and grants:
  - RLS is on all 12 tables. `anon` has nothing.
  - `authenticated` can only `SELECT` member rows, and only safe columns of `organizations`; `policy_json`, `runtime_json` and approval keys are not readable.
  - `connections`, `tasks` and `actions` have no client grants. No client can write anything.
- Storage: a private bucket, `evidence`. Reads require membership of the organization named by the first path segment. Writes go through the service role only.

## Code
- `services/core`:
  - `config.py`: settings plus the `.env` loader.
  - `db.py`: the connection pool. Sessions run in UTC, statements are not prepared (safe behind poolers), and connections autocommit outside explicit transactions.
  - `admin.py`: the `seed-org` and `purge-org` commands, and a dev-only seller connection seed.
  - `campaigns.py`: the launch transaction and the mission read.
  - `errors.py`.
- `services/api`:
  - `auth.py`: JWKS for ES256/RS256 or a secret for HS256; checks `iss`, `aud=authenticated` and `exp`; then looks up membership.
  - `campaigns.py`, `health.py`, `errors.py`.
- `services/worker`:
  - `queue.py`: claim with `SKIP LOCKED` plus a `lease_generation` increment, heartbeat, `fenced()`, complete/fail, and an exhausted-task sweep.
  - `actions.py`: prepare, `begin_execute` (prepared to executing, gated by lease, campaign status and suppressions), `record_result`, and `expire_executing` (executing to unknown, plus one `reconcile_action` task).
  - `main.py`: single-worker heartbeat guard and loop. No production handlers yet.

## Checks actually run
All database runs used a **throwaway local Postgres 16** with `tests/backend/sql/supabase_local_shim.sql`, in `OUTCOME_TEST_AUTH_MODE=local_jwt` with HS256 tokens. **Not Supabase.**

- With the database configured: `pytest` → 107 passed, 5 skipped. The 5 skipped are the Data API (PostgREST) and Storage API checks, which need the real project.
- Without a database: `pytest` → 56 passed, 56 skipped (the database tests, with the reason stated).
- Mutation checks:
  - Dropping the `lease_until > now()` fence made the expired-lease test fail.
  - Dropping the `lease_generation` fence made the restarted-same-`WORKER_ID` test fail.
- Real stack run: `uvicorn` plus `services.worker.main` against the local database.
  - `/health/ready` returned 200 with a fresh worker.
  - `POST /campaigns` returned 202; a replay returned 202 with the same campaign; a changed body returned 409.
  - One `normalize_mission` task was `ready`, and a `campaign_launch` decision was `accepted`.
- Provider calls: none. No Google, Crustdata or Azure.

## To run on Supabase once `.env` exists
1. Apply the migration: `psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f db/migrations/0001_b2_foundation.sql`.
2. Run the suite: `.venv/bin/python -m pytest -rs`. Without `OUTCOME_TEST_AUTH_MODE` it runs in gotrue mode: real users through the Auth admin API, real tokens, and the PostgREST and Storage checks.
3. Create an organization: in Supabase Auth, create the owner user, then run `python -m services.core.admin seed-org --name ... --owner-email ... --buyer-test-email ... --consent-record ... [--approve-placeholder-profile]`.
4. Run the worker: set `RUNTIME_ORGANIZATION_ID` and `WORKER_ID`, then `python -m services.worker.main`.

## Limitations
- Supabase-specific behavior is unverified until it runs on your project: JWKS signing, PostgREST and Storage enforcement, and the `storage.objects` policy on the real storage schema.
- `--approve-placeholder-profile` is a stand-in until B3's profile approval; B3 should make launch reject placeholder profiles.
- The seller connection only passes launch checks when seeded or produced by D2's OAuth.
- There are no task handlers yet, so `normalize_mission` tasks stay `ready`. `MissionDetail` prospects, conversation, evidence and handoff are always empty or null.
- Readiness depends on `RUNTIME_ORGANIZATION_ID`. Without it, the worker reports as `missing` and the endpoint returns 503.
